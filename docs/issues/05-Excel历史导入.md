一次性导入命令，把用户的实习投递 Excel（`E:\24-10-LLH\实习投递.xlsx`，35 条记录）转换成公司、投递、事件三层数据入库。

## 2. 背景

这批数据不只是历史归档，它是**数据模型的验收测试**——真实数据会暴露模型缺陷，而现在改的成本最低。

导入完成后系统立刻不是空的，用户有 35 条真实记录可以维护，这直接影响他会不会持续使用这个系统。

### 源数据形态

完整观察见 [`docs/DESIGN.md`](../DESIGN.md) 附录。核心特征：

```
B1=投递日期  C1=状态  D1=一面        ← 表头只有三列
A11=拼多多 | B11=3.17 | C11=当天测评，29笔试，4.7约面试时间 | D11=4.10一面 | E11=4.14 二面，4.17挂了
                                                                        ↑ E 列有数据但没有表头
A23=腾讯元宝 | C23=捞起来 4.23一面 | E23=4.28二面，4.30挂了   ← 没有投递日期，是被捞的
A16=字节- 抖音搜索 | B16=4.1100000000000003                    ← 浮点误差
```

## 4. 详细规格

### 4.1 解析约束

- **不能依赖表头**。表头只到 D 列，但 E 列有数据。要按列位置和内容处理
- **一个单元格常含多个事件**，如「当天测评，29笔试，4.7约面试时间」要拆成三条 event。这是因为真实记录粒度本就是事件流，只是被二维表压扁了
- 日期形如 `3.11`，无年份，补 **2026**；`4.1100000000000003` 是 Excel 浮点误差，需 round 到 2 位小数
- Excel 解析不要为此引入重型依赖。xlsx 本质是 zip + XML，标准库即可解析；如需要库，选轻量的

### 4.2 公司与业务线拆分

公司名如「字节 - 豆包」「字节- 抖音搜索」「字节 -跨境电商」空格位置各不相同，需拆成 `company=字节跳动` + `businessUnit=豆包`，并把原始写法写入 `companyAlias` 表。腾讯同理（腾讯、腾讯元宝、腾讯云智、腾讯视频）。

### 4.3 特殊行的处理

| 源数据情况 | 处理方式 |
|---|---|
| 无投递日期（腾讯元宝、腾讯视频） | `channel=被捞`，`appliedAt` 留空，首个事件是 `REVIVED` |
| 只有公司名 + 投递日期、无后续（16 条） | **只导入一条 `APPLY` 事件，不要臆造任何后续状态** |
| 「简历没过，应该是还在 cd」这类带主观推测 | 原文必须保留到 `event.rawText` |

### 4.4 关键约束

- **本片不使用 LLM**。JH-06 可能尚未完成，且 35 条数据量很小。用规则拆解，**无法自动解析的内容保留原文到 `event.rawText` 并标记为待人工确认**，绝不静默丢弃
- **导入必须幂等**，重复执行不产生重复数据

- [ ] 35 条记录全部导入，无遗漏

- [ ] 导入后跑一次全量重算，状态与导入时一致

## 7. 验证步骤

```powershell
pnpm --filter server import:excel -- --file "E:\24-10-LLH\实习投递.xlsx"

# 幂等性验证：再执行一次，记录数不应变化
pnpm --filter server import:excel -- --file "E:\24-10-LLH\实习投递.xlsx"

# 一致性验证：重算后状态应与导入时完全相同
pnpm --filter server recompute

pnpm dev
# 手测清单：
# 1. 公司卡片中「字节跳动」应含 3 条（豆包/抖音搜索/跨境电商），「腾讯」应含 4 条
# 2. 拼多多详情页应有多条 event（测评、笔试、约面、一面、二面、挂）
# 3. 腾讯元宝：appliedAt 为空、channel=被捞、首个事件是 REVIVED、最终 CLOSED
# 4. 360/众安保险/联想等 16 条：只有 APPLY 事件，stage=APPLIED、ball=THEM
# 5. 待确认列表中应能看到无法自动解析的原文条目
```
