## 1. 目标

`projectDossier` 表 + 扫描 `data/dossiers/` 目录下的 Markdown 档案 + 页面展示与管理。

**档案由 Cursor 在本系统之外生成。本系统只负责读取、索引、展示，不实现任何代码阅读能力。**

---

## 2. 背景

档案的内容包括：背景、架构、关键技术选型及理由、个人负责部分、量化数据、已知短板、可能被追问的点。

档案的范围**由简历决定，而非由代码决定**——面试官只会顺着简历上的三五行追问。用户最大的项目约 3.2 万行代码（Turborepo，apps 22069 行 + packages 9616 行，468 个文件），但真正需要写进档案的可能只对应两三千行。

一个重要的事实认知：**绝大多数面试问题不需要读代码**。「为什么选 Kafka 不选 RabbitMQ」「QPS 多少」「流量翻十倍怎么改」的答案不在代码里，在设计决策和数据里。这就是为什么一份人工校对过的档案比任何自动代码检索都有用。

## 4. 详细规格

### 4.1 扫描与索引

- 扫描 `data/dossiers/` 目录，解析 Markdown 的 frontmatter（项目名、仓库路径、简历要点）
- 档案文件变化后能重新索引
- `resumeBullets` 存简历要点，JH-12 的简报和模拟面试会用它来关联题目
- 能把档案关联到题库中的项目类问题

### 4.2 这是一个明确的架构决策边界

不要试图「顺手把它做全」：

- **不要实现 code agent**（读文件、grep 的 tool loop）。档案是低频产物——一个项目一辈子写一次，之后小修小补。为低频操作建一整套 agent 基础设施投入产出比过低
- **不要做代码向量索引 / RAG**。代码的 embedding 检索效果一般，工程量大，代码一改就要重建索引
- 不要试图自动扫描用户的代码仓库生成档案

### 4.3 空目录提示

目录为空时要有友好提示，说明档案应由 Cursor 生成并放入该目录（而不是报错或空白页）。

## 7. 验证步骤

```powershell
pnpm --filter shared build
pnpm typecheck
pnpm test

pnpm dev
# 手测清单：
# 1. 清空 data/dossiers/ —— 页面应显示友好提示，说明档案由 Cursor 生成
# 2. 放入一份带 frontmatter 的档案 Markdown —— 应被识别，项目名/仓库路径/简历要点解析正确
# 3. 直接用编辑器修改该档案内容后触发重索引 —— 页面应显示新内容
# 4. 把档案关联到题库中一条项目类问题 —— 关联应持久化

# 确认未引入代码检索类依赖
rg -i "embedding|vectordb|chromadb|faiss" package.json apps packages   # 预期无匹配
```

## 8. 不做

- **实现 code agent**（读文件 / grep 的 tool loop）
- **代码向量索引 / RAG**
- 自动扫描用户代码仓库生成档案
- 在系统内提供档案编辑器（用户用 Cursor 或任意编辑器改 Markdown）
- 参考答案生成、简报、模拟面试（JH-12）
