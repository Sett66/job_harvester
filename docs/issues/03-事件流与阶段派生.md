# 03. 事件流与阶段派生

**类型**：AFK
**依赖**：02 投递记录 CRUD
**先读**：`docs/DESIGN.md` 4.2（阶段的二维建模）、4.3（事件类型）、4.4（表结构）、第 2 节原则 1 和 2

## 要构建什么

这是整个系统的核心机制。包含三部分：

1. `event` 表 + 添加/编辑/删除事件的 API
2. **从事件派生投递状态的纯函数**（本片最重要的产出）
3. 投递详情页的事件时间线

派生函数的签名大致是：输入一条投递的全部事件（按 `occurredAt` 排序），输出 `stage`、`ball`、`outcome`、`currentRound`、`currentInterviewType`、`lastEventAt`、`nextDeadlineAt`。

## 派生规则

必须严格按此实现：

| 事件 | 派生结果 |
|---|---|
| `APPLY` | stage=APPLIED, ball=THEM |
| `SCREEN_PASS` | stage=SCREENING, ball=THEM |
| `SCREEN_FAIL` | stage=CLOSED, outcome=REJECTED, ball=null |
| `ASSESSMENT_INVITE` | stage=ASSESSMENT, ball=**ME**, nextDeadlineAt=事件的 deadlineAt |
| `ASSESSMENT_DONE` | stage=ASSESSMENT, ball=THEM, 清除 nextDeadlineAt |
| `EXAM_INVITE` | stage=WRITTEN_EXAM, ball=**ME**, nextDeadlineAt=事件的 deadlineAt |
| `EXAM_DONE` | stage=WRITTEN_EXAM, ball=THEM, 清除 nextDeadlineAt |
| `INTERVIEW_SCHEDULED` | stage=INTERVIEW, ball=**ME**, currentRound=事件的 round, currentInterviewType=事件的 interviewType, nextDeadlineAt=事件的 scheduledAt |
| `INTERVIEW_DONE` | stage=INTERVIEW, ball=THEM, 清除 nextDeadlineAt |
| `OFFER_INTENT` / `OFFER_FORMAL` | stage=OFFER, ball=null |
| `REJECTED` | stage=CLOSED, outcome=REJECTED, ball=null |
| `WITHDRAWN` | stage=CLOSED, outcome=WITHDRAWN, ball=null |
| `REVIVED` | 从 CLOSED 恢复到被终止前的环节，ball=THEM，清除 outcome |
| `NOTE` | **不改变任何状态** |

`REVIVED` 的实现需要特别注意：它要把投递从 `CLOSED` 拉回进行中，恢复到 `REJECTED` 事件之前的状态。这不是假想场景——真实数据中腾讯元宝走的是「无投递记录 → 被捞起 → 一面 → 二面 → 挂」，腾讯视频是「5.15 捞起来 → 5.20 一面」。

## 关键约束

- **派生函数必须是纯函数**，放在 `packages/shared`，前后端都能调用。不要写成依赖数据库的 service 方法
- `application` 表上的 `stage` / `ball` / `currentRound` / `lastEventAt` / `nextDeadlineAt` 都是**从事件派生的冗余缓存**，存在的唯一目的是方便排序和筛选。必须提供一个「全量重算」命令，任何时候都能从 `event` 表重建这些字段，且结果与增量更新完全一致
- `event.rawText` 保留原始文本片段。像「简历没过，应该是还在 cd」这种带主观推测的记录，原文必须留着，不允许在结构化时丢弃
- 事件可以手动添加、编辑、删除，删除后状态要自动重算
- 时间线要能显示事件类型、发生时间、来源（邮件/手动/导入）和原文

## 验收标准

- [ ] 能给投递添加事件，投递的当前状态自动更新
- [ ] 详情页显示按时间排序的事件时间线
- [ ] 派生纯函数有单元测试，至少覆盖：完整正常流程、`REVIVED` 复活、`NOTE` 不改变状态、多轮面试轮次正确递增、`ASSESSMENT_INVITE` 把球放到 ME 且带截止时间
- [ ] 有全量重算命令，对已有数据重算后结果与增量更新一致
- [ ] 删除中间某个事件后，状态能正确重算
- [ ] 用腾讯元宝的真实案例做一个测试：无投递 → REVIVED → INTERVIEW_SCHEDULED(1) → INTERVIEW_DONE → INTERVIEW_SCHEDULED(2) → REJECTED，最终状态正确
