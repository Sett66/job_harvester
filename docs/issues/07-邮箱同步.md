## 1. 目标

连接 QQ 邮箱，把邮件同步到 `email` 表，页面提供手动同步按钮和邮件列表。

**本片不做任何解析和分类**——那是 JH-08、JH-09 的事。这里只负责把邮件原封不动地搬进来。

---

## 2. 背景

本片是原则 1（原始数据不可变）的直接体现：邮件原文入库后永久保留，后续解析逻辑无论怎么改进，都不需要重新拉邮箱。这决定了 JH-08 和 JH-09 可以放心地反复重跑。

同步之所以只做手动按钮，是因为开发期需要对同一批邮件反复重跑解析，后台定时任务会干扰调试。定时同步留给 JH-13。

## 4. 详细规格

### 4.1 两个必踩的坑

**坑一：QQ 邮箱会拒绝未发送 `ID` 命令的客户端。** 直接登录会报 `Unsafe Login. Please contact xiaoma@qq.com for help`。登录后必须发送 `ID` 命令声明客户端信息才能正常使用。

**坑二：招聘邮件不一定在 `INBOX`。** QQ 邮箱的自动分类会把不少 HR 系统发的邮件归入「订阅邮件」文件夹，部分还会进垃圾箱。**只扫 `INBOX` 一定会漏邮件**，必须遍历多个文件夹。

### 4.2 连接与认证

- 服务器 `imap.qq.com:993` SSL，认证方式是**授权码**（不是 QQ 密码，也不需要 OAuth）
- 用 `imapflow` 做 IMAP 客户端、`mailparser` 解析邮件格式，二者同一作者维护
- **授权码存系统凭据管理器**（`keytar` / Windows 凭据管理器），不写 `.env`、不入库。数据库只存邮箱地址

### 4.3 同步范围与增量

- 回溯范围从 **2026-03-01** 起，做成配置项
- `syncState` 表记录每个文件夹的 `lastUid`，支持增量同步
- 同步中断后再次执行要能续传，不从头开始

### 4.4 存储策略

- **大 HTML 正文落盘**到 `data/mails/`，数据库只存路径；纯文本正文入库便于搜索
- 附件落盘到 `data/attachments/`，`attachment` 表存元信息

### 4.5 容错

- **单封邮件解析失败不能中断整批同步**，记录错误继续处理

## 6. Acceptance criteria

- [x] 点击同步按钮能拉取邮件并入库

- [x] 「订阅邮件」等多个文件夹都被扫描到

- [x] 邮件列表页可查看发件人、主题、时间、正文
- [x] 大 HTML 正文已落盘，数据库中只有路径
- [x] 附件已下载到 `data/attachments/`
- [x] 单封邮件失败时同步继续，错误被记录
- [x] 中断后再同步能从断点继续
- [x] 授权码不出现在代码、配置文件和数据库中

## 7. 验证步骤

```powershell
# 首次运行前，把 QQ 邮箱授权码写入系统凭据管理器（提供一条 CLI 或首启引导）
pnpm --filter server mail:set-credentials

pnpm typecheck
pnpm test
pnpm dev

# 手测清单：
# 1. 点同步 —— 不应出现 Unsafe Login
# 2. 检查日志中被扫描的文件夹列表 —— 必须包含「订阅邮件」，不能只有 INBOX
# 3. 再点一次同步 —— 邮件总数不应增加（messageId 唯一）
# 4. 同步中途强行终止进程，重启后再同步 —— 应从 lastUid 续传
# 5. 检查 data/mails/ 与 data/attachments/ 有文件落盘，数据库中只有路径

# 凭据隔离验证：全仓不应出现授权码
rg -i "授权码|authcode" --glob "!docs/**"   # 预期无硬编码值
```

## 8. 不做

- **任何解析、分类、抽取**（JH-08 粗筛、JH-09 抽取）
- **定时任务**（JH-13）。开发期需要对同一批邮件反复重跑，后台任务会干扰调试
- **IMAP IDLE**。招聘邮件晚十五分钟看到不影响任何决策，不值得维护长连接重连逻辑
- OAuth（QQ 邮箱用授权码即可）
- 把授权码写入 `.env` 或数据库
- 邮件与投递记录的关联（JH-09）
