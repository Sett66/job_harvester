# 10. 面试记录录入 + 题库 + 追问 + 语雀导入

**类型**：AFK
**依赖**：03 事件流与阶段派生、06 LLM 服务层
**先读**：`docs/DESIGN.md` 6.1（复盘录入）、4.4 中的 `interviewNote` 和 `question` 表、第 2 节原则 3

## 要构建什么

面试复盘的完整闭环，四部分：

1. **随手倒文本的录入入口** → LLM 结构化成题目条目
2. **`question` 题库**，本模块的核心资产
3. **Agent 克制追问补全**
4. **语雀历史题目的一次性导入**

## 关键约束

**录入摩擦是这个功能唯一的生死线。** 面试刚结束时人是疲惫的，任何需要填十个字段的表单都会在两次之后烂尾。已验证的事实：用户过去的记录（语雀）只有题目、没有回答，正是因为记录成本太高。

- **主入口是一个大文本框，不是结构化表单。** 用户会倒的内容粒度类似「问了 MySQL 索引、Redis 缓存穿透、我项目那个消息队列为啥选 Kafka，第三个答崩了」，要能从这种程度的输入里提取出题目
- 原始输入**完整保留**到 `interviewNote.rawDump`，永不覆盖（原则 1）
- **追问必须克制**：只针对关键且缺失的点问两三句，**最多 3 轮**。重点是捞出「你当时怎么答的、哪里卡住了」——这层信息价值最高且流失最快（面完两小时就忘一半）。逐条盘问会让这个功能变成负担，直接烂尾
- 面试记录**同时以 Markdown 落盘**到 `data/notes/`，数据库只存路径。这样用户能用任何编辑器打开、能 git 管理、能在系统外搜索（原则 3）
- `question` 表是本模块最重要的产出。**面试记录是原材料，题库才是可复用资产**——第 12 片的简报和模拟面试本质上都是对这张表的查询

**语雀导入部分**：

- 用户会手动把语雀知识库导出成 Markdown 放进一个目录，系统读取该目录批量结构化
- **历史记录只有题目、没有回答**，所以 `myAnswer` 留空，`source=IMPORT`
- 历史题目可能无法关联到具体投递，`applicationId` 和 `companyId` 允许为空
- 导入结果进人工确认，不要直接入库
- 导入必须幂等

## 这批数据的特殊价值

用户还没开始秋招面试，但已有十几二十场实习面试的历史题目。导入后可以立刻做一件高价值的事：结合项目档案为这些题目生成参考答案，用户逐题自评，**在秋招第一场面试之前就产出一份针对性复习清单**。所以题库的 `status`（`NEW` / `WEAK` / `REVIEWING` / `MASTERED`）和 `selfRating` 字段要从第一天就可用。

## 验收标准

- [ ] 倒一段口语化文本能产出结构化的题目条目
- [ ] 原始输入完整保留，可随时查看
- [ ] 追问不超过 3 轮，且只问缺失的关键信息
- [ ] 面试记录正确落盘为 Markdown，可被外部编辑器打开
- [ ] 题目正确写入 `question` 表并关联到投递和面试事件
- [ ] 语雀历史 Markdown 能批量导入，`myAnswer` 为空，进确认队列
- [ ] 语雀导入幂等，重复执行不产生重复题目
- [ ] 题库页面可按公司、分类、掌握状态筛选
- [ ] 能手动修改题目的 `selfRating` 和 `status`
