## 1. 目标

面试复盘的完整闭环，四部分：

1. **随手倒文本的录入入口** → LLM 结构化成题目条目
2. **`question` 题库**，本模块的核心资产
3. **Agent 克制追问补全**
4. **语雀历史题目的一次性导入**

---

## 2. 背景

**录入摩擦是这个功能唯一的生死线。** 面试刚结束时人是疲惫的，任何需要填十个字段的表单都会在两次之后烂尾。已验证的事实：用户过去的记录（语雀）只有题目、没有回答，正是因为记录成本太高。

### 这批数据的特殊价值

用户还没开始秋招面试，但已有十几二十场实习面试的历史题目。导入后可以立刻做一件高价值的事：结合项目档案为这些题目生成参考答案，用户逐题自评，**在秋招第一场面试之前就产出一份针对性复习清单**。

所以题库的 `status`（`NEW` / `WEAK` / `REVIEWING` / `MASTERED`）和 `selfRating` 字段要从第一天就可用。

## 4. 详细规格

### 4.1 录入入口

- **主入口是一个大文本框，不是结构化表单。** 用户会倒的内容粒度类似「问了 MySQL 索引、Redis 缓存穿透、我项目那个消息队列为啥选 Kafka，第三个答崩了」，要能从这种程度的输入里提取出题目
- 原始输入**完整保留**到 `interviewNote.rawDump`，永不覆盖（原则 1）
- 面试记录**同时以 Markdown 落盘**到 `data/notes/`，数据库只存路径。这样用户能用任何编辑器打开、能 git 管理、能在系统外搜索（原则 3）

### 4.2 追问策略

**追问必须克制**：只针对关键且缺失的点问两三句，**最多 3 轮**。

重点是捞出「你当时怎么答的、哪里卡住了」——这层信息价值最高且流失最快（面完两小时就忘一半）。逐条盘问会让这个功能变成负担，直接烂尾。

### 4.3 题库

`question` 表是本模块最重要的产出。**面试记录是原材料，题库才是可复用资产**——JH-12 的简报和模拟面试本质上都是对这张表的查询。

### 4.4 语雀导入

- 用户会手动把语雀知识库导出成 Markdown 放进一个目录，系统读取该目录批量结构化
- **历史记录只有题目、没有回答**，所以 `myAnswer` 留空，`source=IMPORT`
- 历史题目可能无法关联到具体投递，`applicationId` 和 `companyId` 允许为空
- 导入结果进人工确认，不要直接入库
- 导入必须幂等

## 8. 不做

- **结构化表单作为主入口**（录入摩擦是生死线，必须是大文本框）
- 逐条盘问式追问（超过 3 轮即违规）
- 面试录音 + 转写（合规与道德问题，见 DESIGN.md 第 10 节）
- 继续在语雀记录 + 双向同步（历史一次性导入，之后只写系统）
- 语雀 API 对接（用户手动导出 Markdown 即可）
- 参考答案生成、模拟面试、简报（JH-12）
- 读取项目代码（JH-11 只读 Cursor 生成的档案）
