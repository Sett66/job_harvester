## 1. 目标

在骨架基础上加入 `application` 表和完整的增删改查，页面按公司聚合展示投递列表。

同时建立 `companyAlias` 表（JH-09 会用到，本片先建表并支持手动维护即可）。

---

## 2. 背景

本片确立的枚举值会被 JH-03 的派生函数、JH-04 的看板分栏、JH-05 的导入、JH-09 的抽取全部依赖。**枚举定错的代价远高于 CRUD 写得不漂亮**，所以本片的重点是把 `stage` / `ball` / `outcome` / `interviewType` 四组枚举严格对齐 DESIGN.md 4.2。

页面之所以按公司聚合而非大平铺表格，依据来自真实数据：「字节-豆包」「字节-抖音搜索」「字节-跨境电商」是三条独立流程，腾讯有四条。平铺表格会让同一公司的多条投递散落在列表各处。

## 4. 详细规格

### 4.1 表结构

字段定义见 [`docs/DESIGN.md`](../DESIGN.md) 4.4 的 `application` 表与 `companyAlias` 表。

### 4.2 唯一性与重复检测

**一条投递 = 公司 + 业务线 + 批次。** 岗位只是记录字段，不参与唯一性判断（秋招不会给同一业务线投多个岗位）。

**不要加数据库层唯一约束。** 中小公司没有业务线概念，该字段为空，而 SQLite 中 `NULL != NULL`，唯一约束形同虚设。改为应用层重复检测：新增时若已存在相同的公司 + 业务线 + 批次，给出提示但**允许用户继续创建**。

### 4.3 关键约束

- `appliedAt` 可空。被捞起的记录没有主动投递日期（真实案例：腾讯元宝、腾讯视频）
- `channel` 需要包含「被捞」这个取值，其余为官网、内推、牛客、BOSS
- `stage`、`ball`、`outcome`、`interviewType` 的枚举值**必须严格按 DESIGN.md 4.2 定义**，不要自创
- 本片中 `stage` / `ball` 先支持手动设置。从事件自动派生是 JH-03 的事，但**枚举必须现在就定对**
- 页面**按公司聚合展示**：一家公司一张卡片，内含该公司下的若干条投递
- 所有 schema 定义在 `packages/shared`

### 4.4 表单组件的复用要求

新增/编辑投递的表单组件会被 **JH-09 的人工确认队列直接复用**（手动添加投递和确认候选事件本质是同一件事）。因此该组件要做成可独立调用、可预填初值的形式，不要把它和列表页耦合死。

## 6. Acceptance criteria

- [ ] 能新增、编辑、删除投递记录
- [ ] 业务线为空时一切正常，不报错
- [ ] 新增时若存在相同「公司 + 业务线 + 批次」，给出重复提示，但不阻止创建
- [ ] 列表页按公司聚合，一家公司一张卡片
- [ ] 能关联到已有公司，也能在新增投递时顺带创建新公司
- [ ] 枚举值与 `DESIGN.md` 4.2 完全一致
- [ ] Zod schema 定义在 shared 包中，前后端共用
- [ ] 投递表单是可独立调用、可预填初值的组件（供 JH-09 复用）


## 8. 不做

- **数据库层唯一约束**（理由见 4.2）
- 从事件派生 `stage` / `ball`（JH-03）
- `event` 表（JH-03）
- 看板视图、今日待办、沉寂检测（JH-04）
- 别名的模糊匹配与自动归并（JH-09）——本片只建表 + 手动维护
- 大平铺表格视图
