# 02. 投递记录 CRUD + 列表页

**类型**：AFK
**依赖**：01 项目骨架
**先读**：`docs/DESIGN.md` 4.1（投递记录粒度）、4.2（阶段的二维建模）、4.4（表结构）

## 要构建什么

在骨架基础上加入 `application` 表和完整的增删改查，页面按公司聚合展示投递列表。

字段定义见 `DESIGN.md` 4.4 的 `application` 表。同时需要建立 `companyAlias` 表（第 09 片会用到，此处先建表并支持手动维护即可）。

## 关键约束

- **一条投递 = 公司 + 业务线 + 批次**。岗位只是记录字段，不参与唯一性判断
- **不要加数据库层唯一约束**。中小公司没有业务线，该字段为空，而 SQLite 中 `NULL != NULL`，唯一约束形同虚设。改为应用层重复检测：新增时若已存在相同的公司+业务线+批次，给出提示但**允许用户继续创建**
- `appliedAt` 可空。被捞起的记录没有主动投递日期（真实案例：腾讯元宝、腾讯视频）
- `channel` 需要包含「被捞」这个取值，其余为官网、内推、牛客、BOSS
- `stage`、`ball`、`outcome`、`interviewType` 的枚举值**必须严格按 `DESIGN.md` 4.2 定义**，不要自创
- 本片中 `stage` / `ball` 先支持手动设置。从事件自动派生是第 03 片的事，但枚举必须现在就定对
- 页面**按公司聚合展示**：一家公司一张卡片，内含该公司下的若干条投递。不要做成大平铺表格——用户会给同一家公司的多个业务线分别投递
- 所有 schema 定义在 `packages/shared`

## 验收标准

- [ ] 能新增、编辑、删除投递记录
- [ ] 业务线为空时一切正常，不报错
- [ ] 新增时若存在相同「公司 + 业务线 + 批次」，给出重复提示，但不阻止创建
- [ ] 列表页按公司聚合，一家公司一张卡片
- [ ] 能关联到已有公司，也能在新增投递时顺带创建新公司
- [ ] 枚举值与 `DESIGN.md` 4.2 完全一致
- [ ] Zod schema 定义在 shared 包中，前后端共用
