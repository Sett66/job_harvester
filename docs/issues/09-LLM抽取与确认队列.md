# 09. LLM 抽取 + 人工确认队列 + 公司别名归并

**类型**：HITL（这是每天要用的界面，做完请用户实际处理一批真实邮件后再定型）
**依赖**：03 事件流与阶段派生、06 LLM 服务层、08 规则粗筛
**先读**：`docs/DESIGN.md` 5.2（识别与抽取）、5.3（事件归并）、4.1（投递粒度）、第 2 节原则 4

## 要构建什么

自动化闭环的最后一环。把粗筛为 `SUSPECT` / `RELEVANT` 的邮件交给 LLM 抽取结构化信息，产出候选事件；高置信度自动入库，低置信度进人工确认队列；用户确认时可修正，且修正要反哺规则和别名表。

## 抽取字段

公司、业务线、岗位、事件类型、发生时间、**截止时间**。

**笔试和测评的截止时间必须单独抽取，优先级高于其他所有字段。** 它常写在正文里（「请于 X 月 X 日 24:00 前完成」），是整个系统中唯一一个错过就彻底没机会的信息。

## 事件归并优先级

判断一封邮件属于哪条投递，按此顺序尝试：

1. 邮件线程（`In-Reply-To` / `References` 头）
2. 邮件中显式提到的业务线或岗位名
3. 该公司唯一一条进行中的投递
4. 以上都无法确定 → **进人工确认队列**，不要猜

## 关键约束

- **确认队列的 UI 和写入路径必须复用第 02 片的手动录入组件**。手动添加投递和确认候选事件本质是同一件事，不要做两套
- 公司名归并依赖 `companyAlias` 表的模糊匹配。**用户确认一次，系统永久记住**。真实数据中「字节 - 豆包」「字节- 抖音搜索」空格位置都不同，没有别名表这个问题会反复出现
- **用户的修正要反哺规则**：确认某个发件人域名确实是招聘邮件后，自动把该域名加入第 08 片的粗筛白名单
- 抽取结果与原始邮件**分离存储**。改进 prompt 后要能对历史邮件全量重跑，且**重跑不产生重复事件**（需要有幂等机制，比如以邮件 ID + 事件类型去重）
- **不要追求 100% 准确率**。设计目标是「错误易被发现、修正成本低」。宁可多进队列让用户确认，也不要自动入库一堆错数据
- 置信度阈值做成可配置项
- 抽取失败的邮件要标记状态，不能静默跳过

## 验收标准

- [ ] 能对邮件批量抽取并产生候选事件
- [ ] 高置信度自动入库，低置信度进确认队列
- [ ] 队列支持一键确认、修正后确认、忽略
- [ ] 确认后事件正确挂到对应投递；找不到投递时能当场创建新投递
- [ ] 公司别名确认一次后，后续同名变体自动归位，不再进队列
- [ ] 确认发件人域名后，该域名自动加入粗筛白名单
- [ ] 笔试/测评截止时间被正确抽取，并出现在第 04 片的今日待办中
- [ ] 全量重跑抽取不产生重复事件
- [ ] 在真实邮件上跑一遍，人工检查准确率并记录典型失败案例
