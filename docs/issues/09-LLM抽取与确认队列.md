## 1. 目标

自动化闭环的最后一环。把粗筛为 `SUSPECT` / `RELEVANT` 的邮件交给 LLM 抽取结构化信息，产出候选事件；高置信度自动入库，低置信度进人工确认队列；用户确认时可修正，且修正要反哺规则和别名表。

---

## 2. 背景

本片是原则 4（识别一定会出错，所以人工确认是一等公民）的核心落地。**设计目标不是 100% 准确率，而是「错误易被发现、修正成本低」。**

用户的修正必须能反哺系统，否则同一类错误会在整个秋招期间反复出现——真实数据中「字节 - 豆包」「字节- 抖音搜索」「字节 -跨境电商」空格位置各不相同，没有别名表这个问题会一直折磨用户。

## 4. 详细规格

### 4.1 抽取字段

公司、业务线、岗位、事件类型、发生时间、**截止时间**。

**笔试和测评的截止时间必须单独抽取，优先级高于其他所有字段。** 它常写在正文里（「请于 X 月 X 日 24:00 前完成」），是整个系统中唯一一个错过就彻底没机会的信息。

### 4.2 事件归并优先级

判断一封邮件属于哪条投递，按此顺序尝试：

1. 邮件线程（`In-Reply-To` / `References` 头）
2. 邮件中显式提到的业务线或岗位名
3. 该公司唯一一条进行中的投递
4. 以上都无法确定 → **进人工确认队列，不要猜**

### 4.3 UI 复用要求

**确认队列的 UI 和写入路径必须复用 JH-02 的手动录入组件。** 手动添加投递和确认候选事件本质是同一件事，不要做两套。

### 4.4 修正反哺

- 公司名归并依赖 `companyAlias` 表的模糊匹配。**用户确认一次，系统永久记住**
- **确认某个发件人域名确实是招聘邮件后，自动把该域名加入 JH-08 的粗筛白名单**

### 4.5 幂等与可重跑

抽取结果与原始邮件**分离存储**。改进 prompt 后要能对历史邮件全量重跑，且**重跑不产生重复事件**（需要有幂等机制，比如以邮件 ID + 事件类型去重）。

### 4.6 其他约束

- **不要追求 100% 准确率**。宁可多进队列让用户确认，也不要自动入库一堆错数据
- 置信度阈值做成可配置项
- 抽取失败的邮件要标记状态，不能静默跳过

## 6. Acceptance criteria

- [ ] 能对邮件批量抽取并产生候选事件
- [ ] 高置信度自动入库，低置信度进确认队列
- [ ] 队列支持一键确认、修正后确认、忽略
- [ ] 确认后事件正确挂到对应投递；找不到投递时能当场创建新投递
- [ ] 公司别名确认一次后，后续同名变体自动归位，不再进队列
- [ ] 确认发件人域名后，该域名自动加入粗筛白名单
- [ ] 笔试/测评截止时间被正确抽取，并出现在 JH-04 的今日待办中
- [ ] 全量重跑抽取不产生重复事件
- [ ] 在真实邮件上跑一遍，人工检查准确率并记录典型失败案例

## 7. 验证步骤

```powershell
pnpm --filter shared build
pnpm typecheck
pnpm test

# 批量抽取
pnpm --filter server reextract

# 幂等性验证：再跑一次，event 表条数不应增加
pnpm --filter server reextract

pnpm dev
# 手测清单：
# 1. 确认队列中处理一条 —— 事件应正确挂到投递，UI 与 JH-02 手动表单一致
# 2. 找一封无法归并的邮件 —— 应进队列而非被猜到错误投递上
# 3. 确认一个「字节」变体的别名 —— 再抽取同类邮件应自动归位，不再进队列
# 4. 确认某发件人域名 —— 检查 data/screen-rules.json 白名单已追加该域名
# 5. 找一封笔试通知邮件 —— 截止时间应被抽出，并出现在今日待办最前
# 6. 记录典型失败案例（用于后续 prompt 迭代）

# 抽取后重算派生状态
pnpm --filter server recompute
```

## 8. 不做

- 追求 100% 准确率而减少人工确认
- 归并不确定时靠猜（必须进队列）
- 另做一套投递录入表单（必须复用 JH-02）
- 修改邮件原始数据
- 引入 agent / 工具调用（见 DESIGN.md 第 3 节「关于 Agent」）
- 面试题目抽取（JH-10）
