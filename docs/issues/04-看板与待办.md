# 04. 看板 + 今日待办 + 沉寂检测

**类型**：HITL（这是每天要看的主界面，做完请用户实际使用后再定型）
**依赖**：03 事件流与阶段派生
**先读**：`docs/DESIGN.md` 4.2（阶段的二维建模）、第 7 节（提醒）

## 要构建什么

系统的主界面，三个部分：

1. **看板**：按「球在谁手里」分栏，最左边一栏永远是需要用户动手的事
2. **今日待办**：`ball == ME` 的记录，按 `nextDeadlineAt` 排序
3. **沉寂检测**：长期无响应的记录高亮显示

## 关键约束

- **沉寂是算出来的，不是存出来的**。定义为 `ball == THEM && now - lastEventAt > N 天`。查询时计算，**不落库、不写定时任务去刷新**。存成状态就要维护刷新逻辑，算出来则永远准确（见 `DESIGN.md` 第 2 节原则 2）
- **`ball == ME` 的记录不参与沉寂检测**。对「等你行动」的记录报沉寂毫无意义，那是在提醒用户自己拖延
- 沉寂阈值可配置，默认投递后 21 天、面试完成后 10 天。这两个数字是拍脑袋定的，做成配置项以便实际使用后校准
- 今日待办中，**笔试和测评的截止时间优先级最高**——它是唯一一个错过就彻底没机会的时间点
- 看板按公司聚合展示，一家公司下的多条投递归在一起
- 不做日历导出、不做微信推送、不做系统通知（见 `DESIGN.md` 第 10 节）

## 参考数据分布

真实历史数据中 35 条投递有 16 条属于「投出去之后再无下文」，这是最常见的状态。界面设计要考虑这个分布——不要让沉寂记录淹没了真正在推进的那几条，但也不能让它们完全消失（用户需要定期决定是否手动归档为 `ASSUMED_DEAD`）。

## 验收标准

- [ ] 看板按「球在谁手里」分栏，待我行动在最左
- [ ] 今日待办按截止时间正确排序，笔试/测评截止排在最前
- [ ] 沉寂记录高亮显示，阈值可配置
- [ ] `ball == ME` 的记录不会被标记为沉寂
- [ ] 沉寂状态是查询时计算的，数据库中没有对应的存储字段
- [ ] 能从看板直接跳转到投递详情
- [ ] 能把沉寂记录一键归档为 `CLOSED` + `ASSUMED_DEAD`
- [ ] 空状态和数据量大时（50+ 条投递）都显示合理
