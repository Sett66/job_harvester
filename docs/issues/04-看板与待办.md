## 1. 目标

系统的主界面，三个部分：

1. **看板**：按「球在谁手里」分栏，最左边一栏永远是需要用户动手的事
2. **今日待办**：`ball == ME` 的记录，按 `nextDeadlineAt` 排序
3. **沉寂检测**：长期无响应的记录高亮显示

**这是主干的最后一片——走完 JH-01 → 02 → 03 → 04，系统就是一个可日常使用的手动版进度追踪器。**

---

## 2. 背景

真实历史数据中 35 条投递有 16 条属于「投出去之后再无下文」，这是最常见的状态。界面设计要考虑这个分布——不要让沉寂记录淹没了真正在推进的那几条，但也不能让它们完全消失（用户需要定期决定是否手动归档为 `ASSUMED_DEAD`）。

看板之所以按「球在谁手里」而非按环节分栏：一维环节枚举里，「收到笔试通知但没做」和「笔试做完等结果」都是「笔试」，但前者是有截止时间的紧急待办，后者只是等待。按 `ball` 分栏能让「需要我动手」的事永远聚在最左边一栏。

## 4. 详细规格

### 4.1 沉寂检测

**沉寂是算出来的，不是存出来的。** 定义为：

```
ball == THEM && now - lastEventAt > N 天
```

查询时计算，**不落库、不写定时任务去刷新**。存成状态就要维护刷新逻辑，算出来则永远准确（见 DESIGN.md 第 2 节原则 2）。

**`ball == ME` 的记录不参与沉寂检测。** 对「等你行动」的记录报沉寂毫无意义，那是在提醒用户自己拖延。

阈值可配置，默认投递后 21 天、面试完成后 10 天。这两个数字是拍脑袋定的，做成配置项以便实际使用后校准。

### 4.2 今日待办

`ball == ME` 的记录，按 `nextDeadlineAt` 排序。

**笔试和测评的截止时间优先级最高**——它是唯一一个错过就彻底没机会的时间点，必须排在最前。

### 4.3 关键约束

- 看板按公司聚合展示，一家公司下的多条投递归在一起
- 能从看板直接跳转到投递详情
- 能把沉寂记录一键归档为 `CLOSED` + `ASSUMED_DEAD`
- 空状态和数据量大时（50+ 条投递）都要显示合理

## 7. 验证步骤

```powershell
pnpm --filter shared build
pnpm typecheck
pnpm test    # 沉寂判定纯函数需有单测

pnpm dev
# 手测清单：
# 1. 造一条 ball=THEM 且 lastEventAt 为 30 天前的记录 —— 应被标记沉寂
# 2. 造一条 ball=ME 且 lastEventAt 为 30 天前的记录 —— 不应被标记沉寂
# 3. 造两条 ball=ME 的记录，一条笔试截止在明天、一条面试在下周
#    —— 笔试那条应排在最前
# 4. 把沉寂记录一键归档 —— stage 应变 CLOSED、outcome 变 ASSUMED_DEAD
# 5. 清空数据看空状态；造 50+ 条看密度是否可读

# 确认沉寂未落库
pnpm --filter server db:inspect   # 或直接看 schema：application 表不应有 isStale 之类字段
```

## 8. 不做

- 把沉寂状态落库或用定时任务刷新（违反原则 2）
- 对 `ball == ME` 的记录做沉寂提醒
- 日历 `.ics` 导出（见 DESIGN.md 第 10 节）
- 微信推送、系统通知（同上）
- 拖拽改阶段（`dnd-kit` 为可选增强，不在本片验收范围）
- 统计图表（非主干需求）
